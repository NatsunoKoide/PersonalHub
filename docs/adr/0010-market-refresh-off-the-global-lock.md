# 0010：行情取数与 Api 全局锁的分离

- 状态：已采纳（v1.5.0，2026-10-24）
- 相关：0007（联网可选）、0009（行情数据源与快照）

## 背景

v1.4.0 上线后用户报障：「行情这个板块加载中的时候会影响到下面其他板块
一起加载中」——打开行情页期间，切到任何其他页签都卡在「加载中」。

## 根因

`Api` 层用一把全局 `RLock` 串行化所有暴露给前端的方法
（`src/api.py` 的 `_synchronize`，因为 pywebview 的回调来自不同线程，
共用一个 sqlite 连接必须串行）。而 `market_overview()` 在这把锁里
做完全部联网取数：腾讯报价、东财板块×2、涨跌停×2、币圈板块×2、
VIX、恐慌指数，失败还有重试退避——慢辄十几秒。这段时间里其他页签的
取数请求全部排在锁后面，表现为「一起加载中」。

## 决策

三条，全部围绕一个原则：**慢活不下水，水下不持锁**。

1. **后台刷新服务（`src/market_service.py`）**。进程级单例，所有行情
   联网收拢到一条后台线程：自己的 sqlite 连接、自己的锁，与 Api 全局锁
   无关。对外只暴露 `status()`（读内存标志，毫秒级）。并发只刷一次；
   自动刷新有 60 秒节流（反复切进行情页不该反复打接口），手动刷新
   `force=True` 绕过。失败一律静默，界面继续用本地数据。

2. **`market_overview()` 改为纯本地读**。报价取快照表，汇总与温度取
   `market_aggregates` 缓存表（迁移 004：按 kind 一行，payload 为 JSON）。
   一次后台刷新成功才写缓存，且空结果不覆盖——某个源当场没拿到，
   不许把上一轮的板块榜抹成空白。页面打开毫秒级渲染，数据可能是上一轮
   的，页面上照实标了日期；新数据由轮询补上。

3. **`market_watch_add()` 自己分段持锁**。`_synchronize` 增加
   `SELF_LOCKING` 豁免集合：本地检查与落库持全局锁，中间的联网查价
   不持锁，落库前再查一次重复（防并发抢先添加）。其他页签不该被一次
   查价卡住。

前端配合：打开行情页 = overview 本地渲染 + 踢刷新 + 每 2 秒轮询
`overview`，`syncing` 转 false 即静默替换并停轮询；切走页签立即停轮询。

## 后果

- 行情页打开从「阻塞十余秒」变成「毫秒级 + 后台渐进更新」；
  其他页签全程可用。
- 汇总数据有了本地缓存：断网、数据源抽风时显示上一轮结果，体验反而
  比原来的「空白」好。代价是页面可能显示几分钟前的数据——日期照标，
  刷新按钮随时可强制同步。
- 刷新状态进了进程内存（`status()`），没有落库：重启后从本地数据开始，
  启动时后台会立即刷一轮，语义自然。
- 测试新增并发断言：刷新进行中 `market_overview` 与其他页签接口必须
  立即返回（`test_market_network_never_blocks_other_tabs` 等 6 项）。
  以后谁把联网写回持锁路径，这些测试会红。

## 备选方案

- **给每个方法单独配锁**：不解决根本问题——sqlite 连接是共享的，
  脱离全局锁并行写同一个连接会出事。要么每方法一条连接（浪费），
  要么还是串行。慢活移出锁外才是对症。
- **overview 内部起线程 + evaluate_js 回调**：能省掉轮询，但把线程
  生命周期、窗口关闭竞态都引了进来；轮询 2 秒一次只读本地，成本可忽略，
  换来简单可靠。
